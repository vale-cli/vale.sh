# .vale.ini

Learn how a configuration file is shaped, where Vale finds it, and how several of them combine.

## [The file](.vale.ini.md#the-file)

A configuration is an INI file with three kinds of section. Keys above the first section header apply to the run as a whole. `[formats]` maps file extensions Vale does not know onto ones it does. Every other section header is a glob, and its keys apply to the files that match:

```ini
StylesPath = styles
MinAlertLevel = suggestion
Packages = Microsoft

[formats]
mdx = md

[*]
BasedOnStyles = Vale

[*.{md,mdx}]
BasedOnStyles = Vale, Microsoft
Microsoft.Contractions = NO
```

The [generator](https://vale.sh/generator) writes a starting file. After that, `vale sync` installs whatever `Packages` names, and `vale ls-config` prints the configuration a run would use, with every source resolved.

Each key has one home. A core key under a section, or a section key above the first header, is an error that names the key. A key Vale does not read at all is a warning and is otherwise ignored, so a URL left on a line of its own is noticed rather than silently parsed as a key named `https`.

## [Core settings](.vale.ini.md#core-settings)

| Name                                        | Type       | Description                                                                                                                         |
| ------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| [StylesPath](../keys/stylespath.md)         | `string`   | The directory holding styles and the `config/` assets. Relative to the file that sets it, and it has to exist.                      |
| [Packages](../keys/packages.md)             | `string[]` | What `vale sync` installs into the `StylesPath`.                                                                                    |
| [Vocab](../keys/vocabularies.md)            | `string[]` | Vocabularies to load from `config/vocabularies`. Each must be there.                                                                |
| [MinAlertLevel](../keys/minalertlevel.md)   | `enum`     | `suggestion`, `warning`, or `error`. The `--minAlertLevel` flag overrides it.                                                        |
| [IgnoredScopes](../keys/ignoredscopes.md)   | `string[]` | Inline HTML elements whose text is skipped.                                                                                         |
| [SkippedScopes](../keys/skippedscopes.md)   | `string[]` | Block HTML elements whose text is skipped.                                                                                          |
| [IgnoredClasses](../keys/ignoredclasses.md) | `string[]` | HTML classes whose elements are skipped.                                                                                            |
| [WordTemplate](../keys/wordtemplate.md)     | `string`   | The pattern a word-level token is wrapped in, for languages where `\b` is the wrong boundary.                                        |

## [Format associations](.vale.ini.md#format-associations)

`[formats]` tells Vale to read one extension as another:

```ini
[formats]
mdx = md
```

The association changes how a file is parsed, not what it is called: sections still match the name on disk, so the files above need a `[*.mdx]` section, or one whose glob covers both. Mapping a code or data extension onto a markup one lints the markup embedded in that code or data, such as the Markdown in a language's doc comments.

A second named section, `[asciidoctor]`, holds attributes passed to Asciidoctor when it renders `.adoc` files. See [AsciiDoc](../formats/asciidoc.md).

## [Sections](.vale.ini.md#sections)

A section header is a glob matched against a file's path as Vale was given it. `[*]` is every file, `[*.{md,rst}]` is two extensions, and `[docs/src/*.md]` is one part of the project when Vale runs from its root; see [Globbing](../guides/globbing.md). Sections are read in the order written, and where several match a file, a later one's value wins for that key and that file.

| Name                                              | Type        | Description                                                                                                          |
| ------------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------- |
| [BasedOnStyles](../keys/basedonstyles.md)         | `string[]`  | The styles whose rules run. A later matching section replaces the list rather than adding to it.                     |
| [BlockIgnores](../keys/blockignores.md)           | `string[]`  | Patterns whose matches are removed before parsing, for block-level markup Vale does not know.                        |
| [TokenIgnores](../keys/tokenignores.md)           | `string[]`  | Patterns whose matches are removed before linting, for inline markup Vale does not know.                             |
| [CommentDelimiters](../keys/commentdelimiters.md) | `string[2]` | The pair that opens and closes a comment, so in-text directives work in a format without HTML comments.              |
| [Transform](../keys/transform.md)                 | `string`    | An XSLT 1.0 stylesheet applied to XML before linting.                                                                |
| [View](../keys/view.md)                           | `string`    | A view from `config/views` that extracts the prose from a code, data, or plain-text file.                            |

A comma inside a `BlockIgnores` or `TokenIgnores` pattern is written `\,`, so a quantifier like `{2,}` survives the split.

### [Rules](.vale.ini.md#rules)

Any other key under a section names a rule, `Style.Rule`, and its value switches the rule or sets its level:

```ini
[*.md]
BasedOnStyles = Vale, Microsoft

Microsoft.Contractions = NO       # off
Microsoft.HeadingPunctuation = error
House.Hedging = YES               # on, even if House is not in BasedOnStyles
```

A level set in one section holds for that section's files only, so a rule can be an error in Markdown and a warning in HTML. A rule named on its own, without its style in `BasedOnStyles`, is loaded from its file.

A bracket key adjusts one of the rule's parameters, and holds wherever the rule runs:

```ini
Std.SentenceLength[max] = 30
```

It takes the scalars a rule reads: a number, a boolean, a level name. The keys that make a rule what it is, such as `message`, `tokens`, `swap`, and `exceptions`, are refused, since changing those is authoring and belongs in a style that [extends](styles.md#extending-another-rule) the rule.

## [Search](.vale.ini.md#search)

A run finds its configuration in this order and uses the first that applies:

1. The file named by `--config`.
2. The file named by `VALE_CONFIG_PATH`.
3. The first of `.vale.ini`, `_vale.ini`, `vale.ini`, `.vale`, or `_vale` in the working directory or a directory above it, then in the home directory.

![Vale looks for a configuration file in this order: the --config option, then VALE_CONFIG_PATH, then a .vale.ini searched for from the working directory upwards. The global configuration is always loaded as well, and is read last so it can override the others.](../.gitbook/assets/config-search.svg)

Whichever one is found, the user-level file is read too, underneath it. It lives in the operating system's configuration directory, and `vale ls-dirs` prints the path:

| OS      | Location                                           |
| ------- | -------------------------------------------------- |
| Windows | `%LOCALAPPDATA%\vale\.vale.ini`                    |
| macOS   | `$HOME/Library/Application Support/vale/.vale.ini` |
| Linux   | `$XDG_CONFIG_HOME/vale/.vale.ini`                  |

That file is the place for preferences that hold across every project, and `--no-global` leaves it out of a run. When no project file is found, it is the configuration.

## [Layering](.vale.ini.md#layering)

When more than one file is read, the user-level file comes first and the project's file is laid over it, so where both set a single value, the project's holds: `MinAlertLevel` reads the last one set. A list key gathers every value from every file, in reading order and without duplicates, so a `BasedOnStyles` in the user-level file adds styles to a project's. `StylesPath` is both: each file's path is added, resolved against that file, and the project's is the one new assets are written to.

![The user-level file and the project file are laid over one another: each file's StylesPath is kept, the project's MinAlertLevel wins, and the two BasedOnStyles lists join in reading order.](../.gitbook/assets/config-layering.svg)

```ini
# ~/Library/Application Support/vale/.vale.ini
StylesPath = styles
MinAlertLevel = suggestion

[*.md]
BasedOnStyles = write-good
```

Under a project file that names `ProjectStyle` at `MinAlertLevel = error`, this runs both styles and reports errors: the list joined, and the project's level held.

`vale sync` is the exception. It reads exactly one file, the one the search finds, and installs that file's `Packages`. To install what the user-level file names, point the command at it with `--config`.
